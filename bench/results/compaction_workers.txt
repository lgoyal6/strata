Compaction worker-pool benchmark (tools/compaction_bench)
==========================================================

Machine: Apple M3 Pro (11 cores), 18 GB, macOS 26.5.2 (Darwin 25.5.0), APFS.
Date: 2026-09-08. Compiler: Apple clang, Release (-O2 via CMake Release).

Workload (identical for every configuration, seed 42):
  3,000,000 puts from 4 writer threads, uniform updates over a 2,000,000-key
  space ("k%010u", 100-byte values), write_buffer_size 4 MiB, block cache
  64 MiB, fsync_policy kNever (compaction-bound, not fsync-bound), default
  L0 triggers (4/8/12). After ingest, quiescence is detected from the public
  stats counters (no background counter change for 2 s; compaction wall time
  is the last counter change minus ingest end, so the 2 s confirmation
  window is not billed). Then 200,000 uniform point gets on one thread.

Configurations:
  serial-baseline  main @ 445ad7e (dedicated compaction thread), built with
                   STRATA_BENCH_BASELINE against the public DB::open
  pool-w1/w2/w4    this branch, CompactionScheduler with 1/2/4 workers via
                   DBImpl BackgroundConfig (DB::open default remains 1)

Method: 5 interleaved rounds (serial, w1, w2, w4 per round), fresh database
directory per run, medians reported with [min .. max]. The host ran other
automated tasks intermittently during collection; ingest and read-tail
numbers are noisy (spread shown), while write-amplification and compaction
counts are effectively deterministic (spread < 1%).

What the numbers say
--------------------

- Write amplification is the robust win: 11.5x -> 8.5x (about 26% less
  compaction rewriting) at 2+ workers, identical across every round. While
  an L0->L1 compaction runs, new flushes stack more L0 files, so the next
  L0 merge batches more data per rewrite of L1; a second worker meanwhile
  keeps deeper levels moving. (Hypothesis consistent with the counters:
  same 106 flushes and 48-49 compactions, ~950 MB less compaction output.)
- Compaction backlog never throttled ingest at this dataset: write stalls
  are ~0 everywhere, so extra workers could not buy much ingest throughput.
  The group-commit leader (single WAL append + memtable apply) remains the
  write-path bottleneck, consistent with the known 4-thread YCSB behavior.
- Ingest medians favor the pool (141k vs 175-188k ops/s) but the spreads
  overlap heavily on this shared machine; treat 1 worker as parity with the
  old dedicated thread, not a win.

Where parallelism loses
-----------------------

- Read p99: ~112 us at 2 and 4 workers vs ~12 us at 1 worker (medians).
  Lower write amplification means less merging, and the resulting shape
  (278 MB on disk vs 206 MB at w1) leaves more overlapping data for reads
  to walk. Less compaction work is not free; it is paid on the read tail.
  (The serial baseline's own p99 is too noisy on this host to rank: 9-432 us.)
- 4 workers over 2: no ingest gain (184k vs 188k median), identical write
  amplification, and the only stall event of the whole matrix (160 ms).
  On this workload and machine the crossover is at 2 workers.
- CPU: the pool uses slightly more average CPU (1.6-1.7 vs 1.5 cores) for
  the same logical work when compaction is not the bottleneck.
